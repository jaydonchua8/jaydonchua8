## About

I build production-grade software at the intersection of **systems engineering**, **applied AI**, and **product**. My work spans low-latency market data infrastructure in Java, LLM-backed developer tools, and full stack web platforms shipped end to end — from schema design and API contracts through to interface polish and deployment.

I care about engineering that holds up under load: deterministic data structures, tight memory profiles, measured latency budgets, and tests that encode intent. On the AI side, I focus on applied systems — retrieval pipelines, structured LLM outputs, evaluation harnesses — rather than model research for its own sake.

I operate with a **product engineering mindset**: I scope problems against real users, cut ruthlessly toward a shippable core, instrument what matters, and iterate against feedback instead of speculation.

## Featured Projects

<details>
<summary><b>CME Limit Order Book — Real-Time Market Data Engine</b></summary>

<br/>

A high-performance limit order book that decodes CME market data feeds and reconstructs full depth-of-book state in real time. Built in Java with an allocation-conscious core designed for deterministic behavior under sustained message pressure.

| Attribute | Detail |
| :--- | :--- |
| **Stack** | Java, CME MDP 3.0 / SBE decoding, custom primitive collections, JUnit, Gradle |
| **Scale** | Full-depth book reconstruction across multiple instruments from replayed exchange sessions |
| **Performance** | Zero-allocation hot path, array-backed price levels, O(1) best bid/ask access, sub-microsecond update targets |
| **Security** | Strict input validation on binary frames, bounds-checked decoding, defensive handling of malformed and out-of-sequence packets |
| **Impact** | Reference implementation for exchange protocol decoding, book state machines, and latency-sensitive Java design |
| **Repository** | [View Source →](https://github.com/USERNAME/cme-orderbook) |

The engine separates transport decoding from book state so the matching and depth logic can be tested deterministically against recorded sessions. Sequence-gap detection, snapshot recovery, and incremental refresh handling are implemented as first-class states rather than error paths, which makes the system correct under packet loss instead of merely fast in the happy case.

</details>

<details>
<summary><b>LeetStrat — Conceptual Strategy Trainer for Algorithmic Problems</b></summary>

<br/>

A web platform that trains the part of technical interviews people actually fail: pattern recognition and solution strategy. Instead of asking for a full implementation, LeetStrat asks you to identify the approach, justify the data structure, and state the complexity — then evaluates the reasoning.

| Attribute | Detail |
| :--- | :--- |
| **Stack** | TypeScript, React, Next.js, Tailwind CSS, Node.js, PostgreSQL, LLM evaluation layer |
| **Scale** | Problem catalog spanning core algorithmic patterns with per-user spaced-repetition scheduling |
| **Performance** | Server components with incremental static regeneration, streamed model responses, cached problem metadata |
| **Security** | Session-based auth, row-level access scoping, rate-limited inference endpoints, sanitized user submissions |
| **Impact** | Shifts practice from memorized solutions toward transferable problem-solving strategy |
| **Repository** | [View Source →](https://github.com/USERNAME/leetstrat) |

The hard engineering problem is grading open-ended reasoning reliably. Strategy responses are scored against structured rubrics with constrained model output, so feedback stays consistent across attempts and can be regression-tested like any other deterministic system.

</details>

<details>
<summary><b>Opportunity Matcher — Resume-Driven Opportunity Ranking</b></summary>

<br/>

Upload a resume, receive a ranked set of internships, research positions, scholarships, and organizations — each tiered as **reach**, **target**, or **safety** based on the gap between the candidate profile and role requirements.

| Attribute | Detail |
| :--- | :--- |
| **Stack** | Next.js, TypeScript, Python parsing service, embeddings + vector search, PostgreSQL, S3-compatible storage |
| **Scale** | Multi-category opportunity index with continuous ingestion and deduplication |
| **Performance** | Asynchronous parse-and-embed pipeline, cached candidate vectors, sub-second ranked retrieval |
| **Security** | Encrypted resume storage, scoped signed URLs, PII minimization, automatic document expiry |
| **Impact** | Replaces scattered manual searching with a calibrated, personalized opportunity funnel |
| **Repository** | [View Source →](https://github.com/USERNAME/opportunity-matcher) |

Tiering is the core product insight: a flat relevance list tells candidates nothing about where to spend effort. Scores are calibrated against requirement gaps so the output reads as strategy, not search results.

</details>

<details>
<summary><b>SnapCal — Screenshot to Calendar Event CLI</b></summary>

<br/>

A macOS command-line utility that turns any screenshot of an event — a poster, a group chat, a syllabus screenshot — into a structured calendar entry, without leaving the terminal.

| Attribute | Detail |
| :--- | :--- |
| **Stack** | Swift / Python CLI, vision-language extraction, EventKit integration, native macOS APIs |
| **Scale** | Handles arbitrary unstructured event imagery across posters, messages, and documents |
| **Performance** | Single-command execution with concurrent capture, extraction, and event creation |
| **Security** | Local-first processing, explicit calendar permission scoping, no persistent image retention |
| **Impact** | Collapses a multi-step manual workflow into one command |
| **Repository** | [View Source →](https://github.com/USERNAME/snapcal) |

The design constraint was zero friction: no GUI, no login, no configuration beyond first-run permissions. Ambiguous extractions surface an interactive confirmation step rather than silently writing an incorrect event.

</details>

A social discovery app for finding things to do nearby and keeping a running log of what you actually did. Originally built under hackathon time pressure, then rebuilt with a durable data model and real persistence.

| Attribute | Detail |

| **Scale** | Location-scoped discovery with per-user activity history and social feed |
| **Performance** | Indexed geospatial lookups, paginated feeds, client-side caching for repeat queries |
| **Security** | OAuth authentication, authorization checks on every mutation, coarse location handling by default |
| **Impact** | Turns one-off discovery into a persistent, shareable record of activity |
| **Repository** | [View Source →](https://github.com/USERNAME/wtm) |

The rebuild focused on the data model. Treating an activity as an immutable logged event rather than a mutable row made the feed, history, and sharing features fall out of a single abstraction instead of three parallel ones.
